# sp_boomtown_start 岩壁反差：SkyB 原生上传格式修复

## 现象与原版对照

凸出的大块岩石与背景石壁之间出现突兀的黑褐 / 蓝白反差。用户提供的原版正常受光画面中，左侧岩石本就较暗，中央受暖色局部灯影响，瀑布附近为灰白色；背景石壁没有挂载版中那么亮的蓝灰色。原版临时 `mat_fullbright 1` 后，背景变亮而模型岩石仍较暗，进一步把排查指向世界几何的受光路径。原版测试结束已恢复 `mat_fullbright 0` 并退出。

此前的 detail normal、detail color 与色调映射修复保留。它们修复了各自真实存在的问题，但没有解决本次主要岩壁反差，不能据此宣称原版配色已还原。

## 根因

`MapLoader.CreateLightmapPage` 把 SkyB 的 RGBA 方向数据打包为 `R<<11 | G<<5 | B`，却以 `ImageFormat.RGB565` 创建原生纹理。当前后端会返回非空且 `IsValid()` 为真的纹理，但内容已失真，原有的异常 / 空句柄回退不会触发。

SkyB 在世界 shader 中被解码为 `rgb * 2.007874 - 1`，并通过方向长度和法线夹角计算天空可见性。失真的方向因此会把遮蔽区域错误照亮，令背景石壁呈蓝白色，也放大它与使用独立探针的模型岩石的反差。这不是把岩石底色直接改为白色能正确解决的问题。

原版 `_wld` 顶点程序直接传递 lightmap UV；像素程序的 SkyA RGBM 和 SkyB 方向可见性公式与当前挂载路径一致。本轮没有证据要求翻转 UV、改变探针 Q13 比例、删除局部灯或替换岩石贴图。

## 修复

将 SkyB 上传格式改为当前原生后端正确接收这份数据的 `ImageFormat.BGR565`，保留 R 高位、B 低位的打包布局。同步更正代码注释、日志和开关文档。

默认单级 16 位路径保留，SkyB 仍为 2 字节 / texel；RealTimeB 单级仍使用 BGRA4444。未增加 shader 字段、改变 ABI，也未修改引擎生产代码。

定向测试还发现同一路径的多级 mip 数据顺序错误：原来按 L0→L2 拼接，而原生 API 要求 L2→L0，现已调整为最小 mip 在前。引擎现有 `TextureLoader.DDS.GetMipData` 也明确执行该倒序。这个问题影响启用 `LIGHTMAP_MIPS` 或 120 帧预设的情况；本次地图默认关闭 mip，因此它不是默认画面异常的直接原因。

此外，BGRA4444 多级纹理在原生测试中出现下级失真（32×32 的 mip 1 读回最大误差 195），独立的三色 mip 正控制在当前游戏进程还出现创建失败。多级 RealTimeB 因此改用 RGBA8888，保留正确 mip 过滤；单级继续使用 BGRA4444。原生 4444→RGBA CPU 读回把 nibble 左移 4 位而非重复 nibble，单级量化及该转换的合计最大误差为 22，不能把读回 240 当成 GPU 采样一定也把 1.0 压成 240/255。

## 验证

证据目录：`D:\sbox\sbox-public\.tmp\tf2-rock-matching-20261107`。

- 实际提交的 6 个世界材质表绑定均已核对。SkyA GPU 读回与原始 BSP 字节完全一致；旧 SkyB 的原生读回出现远超量化范围的误差。
- 同一进程、同一克隆相机、固定 retail exposure=1 的单因素实验：只把 SkyB 换成原始 RGBA8888，背景石壁恢复暗灰；只替换 RealTimeB 没有该变化。所有绑定、曝光和临时对象均在 finally 中恢复。
- 用同样原始 SkyB 数据创建 BGR565 后，6 页的 RGB 最大字节误差均为 `(4,2,4)`，符合 565 量化精度；固定相机画面与 RGBA 参考接近。蒸汽、瀑布、武器仍会运动，这些画面不是全帧逐像素相等的证明。
- 新增 `Build/LightmapUploadValidation.cs`：通过真实 `CreateLightmapPage` 路径验证原生纹理读回，覆盖单级和三级 mip；同时用 world ordinary / material-table shader 渲染，对比 RGBA 参考并包含方向纹理的正控制。
- 旧 DLL 上 4 个用例中 3 个失败：4×4 上传最大误差 `(225,241,193)`，32×32 为 `(255,255,250)`；ordinary HDR 参考 `(0.2461,0.4922,0.7383)` 却得到 `(1,2,3)`。旧 table 用例偶然通过，不能据此认为该错误稳定或无害。
- 仅改 BGR565 后，单级上传和两个 shader 用例通过，三级 mip 的基础层仍有 `(196,194,196)` 的最大误差，促成上述 mip 顺序修复。最终测试同时检查每一级 SkyA、SkyB 和 RealTimeB，避免只验证 CPU 字节打包而漏掉原生上传约定。

最终 Developer 构建成功，随后日志文字调整的挂载增量构建也成功。最终定向 Integration 用例 **4/4 通过**；3 个修改的 C# 文件通过 `dotnet format whitespace --verify-no-changes`（实际检查 3 文件、0 改动）。本次没有 shader / ABI 修改，沿用已经编译的 shader。

当前结论针对已复现的 SkyB 上传和岩壁受光错误；未验证所有地图的雾、粒子、反射和原版全帧一致性。重启后的实际地图验收结果另在下面记录。
