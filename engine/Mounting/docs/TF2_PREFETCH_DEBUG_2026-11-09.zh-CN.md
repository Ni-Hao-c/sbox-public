# TF2 贴图预取调试记录（2026-11-09）

## 优先处理的问题

玩家画质已允许使用更大的源 mip，因此先检查后台预取的内存约束与释放路径。

旧 `MaterialPrefetch.Reserve` 在超过 128 MiB 后撤销记账、返回 false；但 `TextureLoader.Prepare` 仍保留数据，并且不给这份数据设置释放回调。材质绑定循环也不接受停止信号。因此旧日志的峰值可能低于实际保留量，worker 可以继续读取同一材质的其他贴图。

## 修正后的状态流

1. worker 开始下一张贴图前检查预算；目标已满则停止这个材质的后续预取。
2. 每个实际保留的 payload 都记账，包括跨过目标的那一份。
3. `Prepare` 返回是否还有余量；缓存材质描述与原始 RPAK 绑定两个入口都遵守这个信号。
4. 主线程 `Load` 接管准备数据时，通过 `ClearPreparation` 归还记账；后续纹理上传保持原有主线程路径。
5. 取消时先阻止新预取、通知取消，再等待已有 worker 结束，然后清空准备数据与队列引用。

预算仅针对预取池尚未交给加载器消费的 CPU 数据。正在解码的 payload、主线程正在上传的数据、GPU 纹理和全进程内存不属于同一个统计口径。128 MiB 是目标预算；最多四个材质 worker 已经开始的解码可以暂时超出它。这里不采用等待主线程释放预算的阻塞策略，避免主线程正在等待材质 worker 时形成循环等待。

## 本轮代码路径核对

- `Map.World` 已按消费次序排列 opaque / translucent / decal / godray / water 的预取顺序，保留这条已有逻辑。
- 材质加载先 `Wait`，随后在 `finally` 中 `Consumed`，所以消费后被移出任务表的 job 已经结束；取消仍会等待任务表内的其余 worker。
- 共享 loader 通过 `_prepareLock` 避免重复读取和重复记账；`ClearPreparation` 清掉回调和数据，后续再次清理不会重复返还。
- 场景缓存释放只丢弃资源引用，保留活跃持有者的纹理；本轮不改写地图、编辑器或克隆场景的资源所有权。
- 删除预取路径中结果无人使用的 `ReadMetadata` 调用。预取池结束后清除 loader、任务、待处理材质和 worker 统计集合的引用。
